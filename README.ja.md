`ja-ai-polish` は、文章に表れる AI っぽさを減らし、自然な日本語に整える Agent Skill です。
brief から日本語を作成する場合にも、既存の下書きを直す場合にも使えます。

仕事のメール、チャット、SNS 投稿、進捗報告、リポジトリ運用、技術記事、公開文章など、
実際の利用シーンに合わせて表現と構成を調整します。その際も、事実、文体、用語、責任関係、
書き手の意図は維持します。

## できること

| ✍️ 直接生成 | 🛠️ 修正 | 🔎 診断 | 🎛️ 調整 |
|---|---|---|---|
| 与えられた事実と制約から、シーンに合う日本語を作成します。 | 下書きを必要最小限の変更で整えます。 | 本文を書き換えず、パターンと根拠を説明します。 | 任意の日本語サンプル 2～5 件から繰り返し現れる特徴を使います。 |

## 対象範囲

仕事のメール、Slack/Teams のメッセージ、SNS 投稿、進捗報告、リポジトリ運用、
Qiita/Zenn の技術記事、チュートリアル、ブログ、note、コミュニティ向け文章に使えます。全シーンで
AI らしい不自然な物理改行を整えますが、意図されたシーン固有の改行は保持します。

日本語を母語としない人が、自分で書いた文章の意味や言い方を残したまま、より自然な日本語に
整える用途にも使えます。

## 基本原則

1. 書き手を推測せず、見える問題を診断する。
2. 文体より先に事実を守る。
3. 表現を禁止語ではなくシグナルとして扱う。
4. 媒体、相手、目的からシーンを選ぶ。
5. 一般ルールより書き手のサンプルを優先する。
6. 生成・修正したすべての文章を監査する。

## すぐに試す

**✍️ 直接生成**

```text
/ja-ai-polish を使って、日本語の Slack 進捗メッセージを書いてください。
事実：API 修正は完了、負荷試験は未実施、担当は佐藤さん、期限は木曜。
完成稿だけ返してください。
```

**🛠️ AI らしさの修正**

```text
/ja-ai-polish を使って、次の日本語の定型感を抑えてください。
数字、製品名、約束はすべて維持してください。mode: edit、intensity: standard。

[下書き]
```

**🔎 診断**

```text
/ja-ai-polish を使って次の日本語を診断してください。書き換えは不要です。
```

## write / edit / detect モード

| モード | 入力 | 出力 |
|---|---|---|
| `write` | 目的、読者、事実、制約を含む brief | 日本語の完成稿と短い生成メモ |
| `edit` | 日本語の下書き | 必要最小限に直した完成稿と修正内容 |
| `detect` | 日本語の下書き | 重要度、ルール ID、根拠、説明、修正案 |
| `auto` | 自然言語の依頼 | 上記モードへ自動振り分け |

`edit` は `minimal`、`standard`、`aggressive` に対応します。長文や文全体の削除候補がある
場合は `bounded` を使い、本文から黙って削除せず候補として分けます。

| 検出シグナル | 標準の対応 | 例1 | 例2 |

| 根拠のない評価 | 入力にある結果、指標、影響を使い、なければ不足を示す | 技術ブログ: `処理時間が20%短くなり、非常に効果的です。` → `処理時間は20%短くなりました。` | Pull Request: `テストは50件すべて通過し、非常に優れた結果でした。` → `テストは50件すべて通過しました。` |

| 接続語の過剰使用 | 論理上の役割がない接続語を外す | 技術ブログ: `速度が上がりました。さらに、メモリ使用量も減りました。` → `速度が上がり、メモリ使用量も減りました。` | 製品ページ: `設定は簡単です。また、導入費用は無料です。` → `設定は簡単で、導入費用は無料です。` |

## Scene Pack

| シーン | 優先するもの |
|---|---|
| 仕事のメール | 目的、依頼、担当、期限、適切な敬意 |
| 仕事のメッセージ | 行動できる文脈と簡潔な連携 |
| SNS 投稿 | 反応誘導ではなく、根拠のある更新や意見 |
| 進捗報告 | 完了、阻害要因、リスク、担当、次の行動 |
| リポジトリ運用 | 再現、検証、互換性、コントリビューターの行動 |
| 技術記事 | 技術的正確さ、根拠、制約、実行可能な詳細、公開用 Markdown 見出し |
| 公開文章 | 根拠のある書き手の声と非定型的な構成 |

## 忠実性の保証

生成・修正の前に、名称、事実、数値、日付、コード、用語、主体—行為—対象、否定、条件、
不確実性、約束の台帳を作ります。完成後は台帳と照合します。不足情報は確認するか明示的に
空け、流暢さのために作りません。

## 書き手の声

2～5 件のサンプルから、文のリズム、文体、主語省略、直接性、句読点、評価語の頻度を
調整します。繰り返し現れる特徴だけを使い、サンプルの事実や特徴的な文を再利用しません。

## 既知の制約

- 自然さは文脈依存であり、表現のブラックリストにはできません。
- 情報の少ない brief から、根拠のある具体性は作れません。
- 法務、HR、学術などの高リスク文書には有資格者の確認が必要です。
- 文章品質を改善する Skill であり、著者を証明するものではありません。
